## 缓存（Redis）

## 1. Redis 简介

Redis 是一种基于内存的键值型数据存储系统，支持字符串、哈希、列表、集合、有序集合等多种数据结构。由于其读写性能高、支持过期时间与丰富的数据操作，常被用作应用缓存层，用于降低数据库访问压力、提升接口响应速度。

## 2. Redis 作为缓存

在系统中引入 Redis 作为缓存时，通常位于应用与数据库之间：

- 应用优先从 Redis 读取数据；
- 缓存未命中时再查询数据库；
- 将查询结果写回 Redis，并设置合理的过期时间。

Redis 适合存储热点数据、频繁读取但更新较少的数据，以及需要临时保存的会话、验证码、计数等信息。

## 3. Redis 服务端安装与客户端配置

### 3.1 安装 Redis 服务端

在服务器或开发环境中安装 Redis 服务端，启动 Redis 服务，并根据需要配置：

- 监听地址与端口；
- 访问密码；
- 持久化策略；
- 最大内存与淘汰策略；
- 日志与数据目录。

### 3.2 配置 Redis 客户端

在应用侧配置 Redis 客户端连接信息，包括：

- 主机地址与端口；
- 密码；
- 数据库编号；
- 连接超时时间；
- 连接池大小。

通过连接池管理 Redis 连接，避免频繁创建和销毁连接带来的开销。

## 4. 封装缓存操作

对 Redis 操作进行统一封装，避免业务代码直接散落 Redis 命令。常见封装内容包括：

-`get(key)`：读取缓存；
-`set(key, value, expire)`：写入缓存并设置过期时间；
-`delete(key)`：删除缓存；
-`exists(key)`：判断缓存是否存在；
- 序列化与反序列化：对象数据通常序列化为 JSON 后写入 Redis，读取时再反序列化。

封装时应统一 key 命名规范，例如按业务模块、数据类型、业务主键组合生成缓存 key，便于维护和排查问题。

## 5. 缓存策略

### 5.1 旁路缓存策略

常用策略为旁路缓存策略（Cache Aside）：

**读操作：**

1. 先查询 Redis 缓存；
2. 缓存命中则直接返回；
3. 缓存未命中则查询数据库；
4. 将数据库查询结果写入 Redis，并设置过期时间；
5. 返回数据。

**写操作：**

1. 先更新数据库；
2. 再删除 Redis 缓存；
3. 后续读取时重新加载最新数据并回填缓存。

该策略实现简单，能够保持缓存与数据库信息基本一致。

### 5.2 过期时间设计

为缓存设置合理的过期时间：

- 避免数据长期不更新导致与数据库不一致；
- 防止大量缓存同时过期；
- 可根据数据更新频率设置不同 TTL。

可在基础过期时间上增加随机偏移，降低缓存雪崩风险。

## 6. 常见缓存问题与应对

### 6.1 缓存击穿

**问题：** 某个热点 key 过期后，大量请求同时访问数据库。

**应对：**

- 使用互斥锁，只允许一个请求重建缓存；
- 热点数据采用逻辑过期，异步更新；
- 对热点 key 设置较长过期时间或永不过期并配合后台更新。

### 6.2 缓存雪崩

**问题：** 大量缓存同时过期或 Redis 服务不可用，导致请求集中打到数据库。

**应对：**

- 过期时间增加随机值，避免同时失效；
- 保证 Redis 高可用；
- 增加限流、降级与熔断措施；
- 数据库层做好压力保护。

### 6.3 缓存穿透

**问题：** 请求查询不存在的数据，缓存和数据库都无法命中，导致请求持续访问数据库。

**应对：**

- 对不存在的数据缓存空值，并设置较短过期时间；
- 使用布隆过滤器提前拦截不存在的 key；
- 对请求参数进行合法性校验。

## 7. 数据一致性

缓存与数据库之间需要关注一致性问题。常见做法包括：

- 先更新数据库，再删除缓存；
- 对一致性要求较高的场景，可采用延迟双删；
- 接受最终一致性，并通过过期时间兜底；
- 对强一致要求高的数据，可减少缓存使用或采用更严格的更新机制。

实际项目中应根据业务对一致性的要求选择策略，避免过度设计。

## 8. 小结

Redis 作为缓存层，核心目标是提升读取性能并降低数据库压力。工程实践中应完成 Redis 服务端安装、客户端配置、缓存操作封装与缓存策略设计，并重点处理缓存击穿、缓存雪崩、缓存穿透以及缓存与数据库的数据一致性问题。
